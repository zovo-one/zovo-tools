Chrome extension ID calculator

By Michael Lip. Updated 2026-11-09.

A Chrome extension ID is 32 letters from a to p, such as ghbmnnjooekpmoecnnnilnnbdlolhkhi for Google Docs Offline. The Chromium source calculates it from the key in manifest.json when the manifest has one, and otherwise from the absolute path of the unpacked folder. In both cases it takes the SHA-256 digest of the input, keeps the first 16 bytes and writes them with those letters. This page runs that calculation in your browser with Web Crypto, and it sends nothing that you paste to a server.

The tool takes a path or a key, and it can compare the result with an ID that you expect.

  • Manifest key or PEM public key. The tool applies the key parsing rules of Chromium and shows the ID. The ID depends only on the key, so the same key gives the same ID on every machine. With the public key of a store item, the result should be the ID of the published version.
  • Absolute folder path. The tool hashes the path with the byte rules of each system and shows each step. The bytes are UTF-8 on macOS, UTF-8 by assumption on Linux, and UTF-16LE with an uppercase drive letter on Windows. When manifest.json has no key and you enter the resolved path, this is the ID that chrome://extensions shows for the unpacked folder. Moving the folder changes it.
  • Expected ID. The tool reports whether its result matches the ID that you enter, and it names the rule behind the result. A key comes before the path, so the path matters only when the manifest has no key.

A store item has its own public key, which the Developer Dashboard shows on the Package tab. An unpacked copy with no key gets its ID from the folder path instead, so its ID differs from the store ID. The Chrome documentation says to copy the public key of the item into the key field to keep one ID during development, and it says that the two IDs should then match.

Calculate the ID

How Chromium calculates the ID

ComputeExtensionID in extensions/common/extension.cc chooses the input. If the manifest has a key, it decodes the value with ParsePEMKeyBytes and passes the bytes to GenerateId. The folder path is used only when there is no key, through GenerateIdForPath. The calculation itself has three steps.

  1. Hash. GenerateId computes SHA-256 over the input bytes.
  2. Keep 16 bytes. The first 16 bytes of the digest (kIdSize = 16) are hex-encoded into 32 characters.
  3. Change the alphabet. Each hex digit from 0 to f becomes a letter from a to p. A comment in the source gives the reason, which is to avoid a completely numeric host, since some software reads that as an IP address.

ParsePEMKeyBytes refuses an empty value and a value above 100 KiB. If the value starts with -----BEGIN, it collapses whitespace, cuts the header up to KEY----- and the footer from -----END, and decodes what is left. Runs of whitespace that contain a line break disappear in that step, a run at the very end disappears too, and other runs become one space. The decoder is strict. The length must be divisible by 4, only the base64 alphabet and final padding are allowed, and any remaining space or line break is an error. A value without a PEM wrapper is decoded as it is, so a line break in it is an error. The tool gives an error for a value that fails these rules, with one exception. It removes spaces and line breaks around a pasted value, and it warns you when Chromium would refuse the value with them.

For a path, Chromium first makes the folder path absolute with MakeAbsoluteFilePath, which calls realpath on macOS and Linux and _wfullpath on Windows. GenerateIdForPath then calls MaybeNormalizePath. On Windows that function changes a lowercase drive letter to uppercase, so c:\ and C:\ give the same ID for the same folder. On other systems it returns the path unchanged. The hash covers the path value in its native form, which is UTF-8 on macOS and UTF-16 code units on Windows, hashed in little-endian order as the Windows test vector shows. Linux does not fix an encoding for paths, and this tool assumes UTF-8 there.

An ID from a path therefore follows the location of the folder. Two machines get the same ID only when the resolved path bytes are the same. To keep one ID everywhere, put a key into manifest.json.

Validate an ID

The IdIsValid function accepts exactly 32 characters from a to p, in upper or lower case. If you paste such an ID into the path box, the tool says that it has this form and gives it in lowercase. The check does not show that an extension with this ID exists.

One-liner for your own machine (macOS or Linux)

python3 -c "import hashlib,os;print(''.join(chr(97+int(c,16)) for c in hashlib.sha256(os.path.realpath('/Users/you/my-extension').encode()).hexdigest()[:32]))"

Replace /Users/you/my-extension with your absolute path. Python's os.path.realpath follows symbolic links, as the realpath call in Chromium does, and the command then hashes the UTF-8 bytes. On macOS it keeps the case that you type, while the realpath call in Chromium can return the case stored on the disk, so type the exact case of each folder name. Do not use this command for a Windows path.

Limits of this tool

  • It does not read your files or your installed extensions. You paste the path or the key as text.
  • It does not open .crx files. In a CRX3 package, crx_verifier.cc requires that the ID in the signed header equals GenerateId of a public key in that header, which is the same calculation as the key form above. To read the ID from a file, use the CRX viewer.
  • It refuses private keys in the forms that it recognizes, in any of the three fields, and it does not hash them or show their bytes. The forms are PEM private key blocks, PuTTY private key files, and bare base64 of PKCS#1, PKCS#8, encrypted PKCS#8, PKCS#12, SEC1 or OpenSSH private key data. The .pem file that Pack Extension writes is a private key. Paste the public key only.
  • It cannot follow a symbolic link, because it cannot see your disk. On macOS and Linux, Chromium resolves the path with realpath before it makes the ID. A path that goes through a symbolic link, such as /tmp on macOS, gives a different ID here unless you paste the resolved path.
  • It trims spaces around the path and removes ., .. and repeated or trailing separators from the text. On Linux that gives the result of realpath when no symbolic link is involved. On macOS it can differ even without a symbolic link, because realpath there can return each name with the case stored on the disk. Enter a macOS path with the exact case of its folder names. On Windows the tool also changes / to \, but Chromium calls _wfullpath there, and whether these text rules match _wfullpath in every case, such as a trailing backslash or a name that ends in a dot, is not verified.
  • How macOS Unicode normalization affects the path bytes that Chromium hashes is not verified. The tool applies no Unicode normalization to the text that you paste.
